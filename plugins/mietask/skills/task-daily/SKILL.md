---
name: task-daily
description: Slack・Gmail・Googleカレンダーを巡回し、自分が対応すべきタスクを親＋子スレッドの形で自分のSlackチャンネルに投稿する。あわせて前日のスレッドに入った「N完了」をタスク台帳に反映する。毎朝の定期実行から呼ばれるほか、「今日のタスク投稿して」「巡回して投稿」と言われたときにも使う。「3は対応不要」「これは要らない」「3は来週にする」「2は〇〇さん待ち」のように、一覧の番号を指してタスクの扱いを変えたいと言われたときも使う。「〇〇の案件は終わった」「〇〇は持っていない」のように、持っている案件の一覧を直したいと言われたときも使う。
---

自分のタスクを巡回し、結果をSlackの自分専用チャンネルに投稿する。
あわせて、前日のスレッドへの返信（完了・ステイ・メモ・追加）を台帳に反映する。

## 置き場所

| | パス |
|---|---|
| 実行ファイル | `${CLAUDE_PLUGIN_ROOT}/bin/mietask`（Mac・Windows 共通。追加のインストール不要） |
| データ | `~/.mietask/`（`MIETASK_HOME` で変更可） |
| 設定 | `~/.mietask/config.json` |

**最初に `$H/config.json` を読む**（`$H` の求め方は下の「Mac でも Windows でも」を参照）。 本人の名前・メール・SlackユーザーID・
投稿先チャンネル、および巡回の除外ルールがそこにある。

設定が無ければセットアップが済んでいない。`/mietask:setup` を案内して止まる。

**`tasks.json` は唯一の正。手で編集しない。** 登録と完了反映は必ず
`mietask sync` を通す（バックアップと原子的な置き換えが入っている）。

**コマンドの打ち方（毎朝の実行が確認画面で止まらないように）**

- 実行ファイルは毎回 `bash "${CLAUDE_PLUGIN_ROOT}/bin/mietask" <コマンド> [引数]` と、パスをそのまま書いて呼ぶ。`B=…` のように変数に入れない
- 1回の Bash で打つのは1つのコマンドだけ。`;` `&&` `|` でつながない。`cd` もしない
- 台帳や設定を `cat`・`python3` などで直接読まない。中身は実行ファイルの出力と Read ツールで見る
- 自動承認モードが使えない会社でも、この形だけは許可に登録してある（`mietask permissions`）。
  外れた形で打つと確認画面で止まり、朝の投稿が届かない

**Mac でも Windows でも同じ手順で動かす。**

- パスは必ず `"…"` で囲む
- 一時ファイルは `/tmp` ではなく `$T` に書く。最初に次の2つを**1つずつ**実行し、出てきた絶対パスを `$H`・`$T` とする。
  `$H`・`$T` はこの手順書の中の呼び名で、シェルの変数ではない。コマンドやツールには、出てきた絶対パスを書き写して渡す。
  Writeツール・Readツールに渡すパスにも `~` を使わず、この絶対パスを使う

```
bash "${CLAUDE_PLUGIN_ROOT}/bin/mietask" paths home
bash "${CLAUDE_PLUGIN_ROOT}/bin/mietask" paths tmp
```

## 1. 前日の返信を反映する

```
bash "${CLAUDE_PLUGIN_ROOT}/bin/mietask" sync thread
```

`ts` が出なければ初回。この節を飛ばして2へ。

`ts` が出たら、そのスレッドを `slack_read_thread`（channel_id はその `channel`、
message_ts はその `ts`）で読み、返信を次の形で `"$T/task-replies.json"` に書く。
**Writeツールで書く。heredoc や `cat >` は使わない。**

```json
[{"user": "U01ABCDEFG", "text": "1完了"}, {"user": "...", "bot_id": "...", "text": "..."}]
```

`user` と `bot_id` は読み取れたものをそのまま入れる。**省略しない。**
Botが投げた子スレッドを本人の発言と取り違えると、無関係なタスクが done になる。

**本人の返信が0件でも、読み取った返信をそのまま書く（Botの子スレッドしか無ければ、それだけを書く）。**
ファイルを書かずに先へ進まない。

```
bash "${CLAUDE_PLUGIN_ROOT}/bin/mietask" sync complete --replies "$T/task-replies.json"
```

**入力ファイルは、使い終わると実行ファイルが消す**（返信・巡回結果・投稿内容のどれも）。
前の実行のファイルが残っていると、書き直せなかったときに古い中身で台帳を書き換えてしまうため。
`見つかりません` / `no such file` と出たら、書き込みに失敗している。**もう一度書いてから**実行する。
古いファイルを探して使い回さない。

返信は次の4種類を受ける。実行ファイルが判別するので、こちらで解釈し直さない。

| 返信 | 反映 |
|---|---|
| `1完了` | done にする。翌日から出ない |
| `2ステイ` | 明日もそのまま出す。相手待ち・保留中のものでも翌朝は必ず出る |
| `3 メモ本文` | そのタスクにメモを残す。翌朝の一覧に「前回のメモ」として出る |
| `追加 見積書を作る 11/20まで` | 新しいタスクとして足す。日付があれば期限になる |

`2ステイ 来週の会議で決める` のようにステイとメモを同時に書いてもよい。

**追加は、巡回で拾えない仕事を本人が手で入れるための道。** 巡回はSlack・Gmail・カレンダー・議事録に
出てきたものしか拾えないので、口頭で頼まれたことや自分で決めた仕事はここから入る。
足したタスクは翌朝の upsert で「巡回では拾われなかったが、未完了なので一覧に載せるもの」として出る。

出力の「⚠ 解決できず」「⚠ 該当なし」は**黙って流さない。** 最後の報告に含める。

### そのほかの書き込みを扱う（一覧を本人に合わせて育てる）

出力に「そのほかの書き込み」（`✎` の行）があれば、本人が上の4つの形に当てはめずに書いたもの。
**捨てずに、1行ずつ次のどれかとして扱う。** 本人はこの場にいないので確かめられない。だから、やったことは必ず投稿で知らせる（4 の子スレッド 7）。

| 書き込み | 扱い |
|---|---|
| 終わったことの報告（「見積書、出しました」「〇〇の件は片付いた」） | `bash "${CLAUDE_PLUGIN_ROOT}/bin/mietask" sync thread` の `mapping` と台帳の題名から、**どれのことか1つに決まるときだけ** `bash "${CLAUDE_PLUGIN_ROOT}/bin/mietask" sync done <id> --quote "<✎の行をそのまま>"`。2つ以上に当たる・どれにも当たらないときは done にせず、投稿で「これのことですか？」と番号つきで聞く |
| 出さなくていいもの（「〇〇社からのメールは要らない」「#〇〇 は見なくていい」） | `$H/config.json` の `gmail.exclude_senders`（送信元のアドレスを台帳のタスクの出所から引く）・`slack.exclude_channels`（チャンネルID）に足す。今出ている該当タスクは `sync status <id> --status dropped --note "本人の書き込み: …"` |
| 一覧の作り方への要望（「出欠確認は出さなくていい」「〇〇さんからの依頼は今日中に入れて」「返信案はもっと短く」） | `$H/config.json` の `requests`（無ければ作る）に `{"text": "<書き込みの要点>", "since": "yyyy-mm-dd"}` を足す。2 の巡回と 4 の組み立てで必ず従う |
| 取り消し（「さっきのは戻して」「〇〇のメールはやっぱり出して」） | 足したものを `config.json` から外す |
| 持っている案件のこと（「〇〇も持っている」「〇〇はもう終わった」） | 下の「会話で扱いを変えたいと言われたとき」の表と同じ（足すなら `touched`、外すなら `remove`。外した案件を戻すなら `restore` も） |
| 新しくやること（「〇〇を作る」） | `追加` と同じ。`"$T/task-findings.json"` に入れて 3 で登録する（`source.ref` は `manual:<スレッドのts>:<書き込みの先頭10文字>`） |
| 分からないもの・あいさつ | 何もしない。意味がありそうなら、投稿で「〇〇はどういう意味ですか？」と聞く |

- `config.json` は **Editツールで、既存の項目を消さずに** 足す。同じものがすでにあれば足さない
- 外すほう（出さない・dropped）にだけ変える。**出す範囲を広げる要望**（「〇〇のチャンネルも見て」）は `requests` に書き、巡回で見るだけにする
- 他人や Bot の書き込みは実行ファイルが落としている。✎ に出たものだけが本人の書き込み

すでに `done` のものは「変更なし」と出る。同じスレッドを二度読んでも、
ステイの回数やメモが二重に増えることはない。

## 2. 巡回する

`task-check` スキルを使って Slack・Gmail・Googleカレンダーを巡回する。
スキルの指示に従いつつ、`config.json` の除外ルールを必ず通す。

**判定軸は「自分が何かをしないと前に進まないか」だけ。** 迷ったら拾う。

`config.json` の `requests`（本人が書き込みで伝えた要望）があれば、**拾う・拾わない・並べ方の判断で必ず従う。**

- **未読・受信トレイ在中は「要対応」の目印に使わない。** 受信トレイを整理していない人が
  多く、未読が数千件あることも珍しくない。`config.gmail` の除外を通してノイズを落とす
- 巡回できなかったサービス（未接続・エラー）は**黙って省略しない。**
  「Notion: 未接続のためスキップ」のように明記する
- 議事録が自動でメールに届く環境なら、そこから**自分の名前が付いたアクションだけ**を拾う
  （`config.meeting_notes`）
- 対面の打合せは議事録が取れない。該当しそうな予定が直前にあれば、その旨を書く

### 最初の1回（1 で `ts` が出なかった日）は深く巡回する

ふだんの朝は前日からの差分だけを見れば足りる（前の日までに拾ったものは台帳に残っていて、翌朝も出る）。
**最初の1回は台帳が空なので、ここで拾い漏らしたものはどこにも残らない。** 急がず、次の範囲を全部見る。

| | 見る範囲 |
|---|---|
| Slack | 直近2週間の、自分へのメンション・DM・自分が発言したスレッドの新着。検索は**次のページがあれば最後まで送る**（1ページ目だけで止めない） |
| Gmail | 直近2週間の自分宛て（`to:me newer_than:14d` と除外）。こちらも結果を最後まで送り、候補は1通ずつ開いて確かめる |
| 議事録 | `from:gemini-notes@google.com newer_than:14d` を**別に検索**し、1通ずつ開いて自分の名前が付いたアクションを拾う（自分宛ての検索だけでは埋もれる） |
| カレンダー | 今日〜2週間先。出欠の未回答と、準備の要る予定 |

- 期限を過ぎていても、まだ済んでいない依頼は拾う（`overdue`）。済んだ跡（自分の返信・送付）があれば拾わない
- 出欠の返事ばかりで埋めない。依頼・宿題・返事待ちを先に探す
- 終わったら、Slack・Gmail・議事録・カレンダーからそれぞれ何件拾ったかを最後の報告に書く（どこかが0件なら、本当に無いのかを見直す）

## 3. 台帳に登録する

巡回で拾ったものを `"$T/task-findings.json"` に書く。**Writeツールで書く。**
**表示したい順**（期限超過 → 今日中 → 今週中 → 予定の確認 → 相手待ち）に並べる。
この配列の順が、そのまま表示番号 1, 2, 3… になる。

```json
[{
  "title": "見積書の内容を確認して返信",
  "section": "overdue",
  "priority": "P1",
  "due": "2026-10-31",
  "due_confidence": "explicit",
  "next_action": "金額の根拠を確認し、問題なければ承認を返す",
  "notes": "",
  "source": {"app":"slack","ref":"slack:C01ABCDEFG:1793867033.987339","url":"https://...","from":"〇〇さん(DM)","activity_at":"2026-10-30T18:20:00+09:00"}
}]
```

- `source.activity_at` は、そのスレッド・メールで**最後に本人以外が発言・送信した時刻**（`2026-10-30T18:20:00+09:00` の形）。
  Slack・Gmail のものには必ず入れる。本人の発言・Bot の投稿・リアクションは数えない。分からなければ入れない。
  完了したタスクでも、完了のあとに相手から修正や追加の依頼が来ていれば、実行ファイルが**続きのタスクとして起こし直す**
  （「完了のあとに動きがあったので起こし直し: t045 ← t012 の続き」と出る。投稿ではほかの新規と同じに扱う）

- `section` は `overdue` / `today` / `week` / `watch` / `waiting` のどれか
- `source.ref` は**突合の唯一の鍵。** Slackは `slack:<channel>:<thread_ts>`、
  Gmailは `gmail:<threadId>`、カレンダーは `calendar:<eventId>`、議事録は `meeting:<id>`。
  同じ案件には必ず同じrefを使う。**ここがブレると毎朝重複登録される**
- `due_confidence` は本文に明記があれば `explicit`、文脈からの推測なら `inferred`
- **推測で金額・期限・担当者を埋めない。** 読み取れないなら notes に「要確認」と書く

```
bash "${CLAUDE_PLUGIN_ROOT}/bin/mietask" sync upsert --findings "$T/task-findings.json"
```

出力の「表示番号 → task.id」を**そのまま使う。** 番号を自分で振り直さない。
「除外」として出たものは投稿に載せない（完了済みで、そのあと動きの無いもの・却下済み）。

**「巡回では拾われなかったが、未完了なので一覧に載せるもの」も必ず投稿に載せる。**
巡回はSlack・Gmail・カレンダーを見るだけなので、台帳にあって今日は誰も触れていない
タスクは、これが無いと永久に沈む。**期限超過を落とすのが最悪。**
出力に区分・ID・期限・次の一手が入っているので、該当区分に混ぜて期限が古い順に並べる。

## 4. 投稿用のpayloadを組み立てる

親メッセージ1本＋子スレッド最大5本（最初の洗い出しの日の 6、書き込みを扱った日の 7 は足す）。番号は3の出力どおり。

**親**
```
:date: *M/D(曜) HH:MM*  :warning:超過N / :red_circle:今日N / :large_yellow_circle:今週N

1. 最重要タスクの見出し ← 一言理由
2. …
3. …

詳細はスレッドに。返信で「1完了」「2ステイ」「3 メモ」「追加 〇〇」が書けます。
:seedling: 終わったこと・要望（「〇〇からのメールは要らない」など）も、このスレッドにそのまま書いてください。翌朝から反映します。
```
上位3件まで。該当0件の区分は件数表記からも落とす。

**子スレッド**（順番を守る。該当0件の区分はスレッドごと省く）

| | 中身 |
|---|---|
| 1 | :warning: 期限超過（全件・次の一手つき・何日超過かを書く） |
| 2 | :red_circle: 今日中 |
| 3 | :large_yellow_circle: 今週中（上位5件＋「…他N件」。黙って切らない） |
| 4 | :calendar: 予定の確認事項／:hourglass_flowing_sand: 相手待ち |
| 5 | :speech_balloon: 返信案（コピペ用のコードブロック） |
| 6 | :thinking_face: 持っているか確かめたい案件（最初の洗い出しの日だけ。4.5 で根拠が弱かったもの。4.5 を済ませてから足す） |
| 7 | :seedling: 書き込みの反映（1 で「そのほかの書き込み」を扱った日だけ） |

7 は、前日の書き込みでやったことと、聞き返したいことを書く。戻し方も添える。

```
:seedling: *昨日の書き込みを反映しました*
• 「見積書、出しました」→ 見積書の確認（t012）を完了にしました
• 「〇〇社からのメールは要らない」→ 〇〇社からのメールは出さないようにしました
• 「出欠確認は出さなくていい」→ 明日から出欠の確認は一覧に入れません
:question: 「資料の件、終わり」は t031（資料の修正）と t035（資料の送付）のどちらですか？「t031完了」のように返してください
戻したいときは「さっきのは戻して」と書いてください。
```

6 は次の形で書く。案件名だけを並べ、推し量った理由は短く添える。

```
:thinking_face: *これも持っている案件ですか？*
カレンダーなどに出てきましたが、手がかりが少ないので一覧には入れていません。
• 〇〇（11/20の会議の題名から）
• △△（10月のやりとりが最後）
持っているものがあれば、このスレッドに「〇〇も持っている」と書いてください（Claude に言っても同じです）。何もなければ入れません。
```

**返信案は省かない。** 次の一手が「返す・返事・回答・出欠」のタスク（相手に返事を返すもの）が1件でもあれば、
5 を必ず付け、そのタスクごとに下書きを1つ書く。`post --dry-run` で「返信案の子スレッドがありません」と出たら、足してから投稿する。

各タスクは `番号. タイトル  \`tNNN\`` → 出所（可能ならpermalink）→ `→ 次の一手: …` の順。

upsert の出力に「前回のメモ・ステイ」があれば、そのタスクの次の一手の下に**そのまま**添える。

```
3. 山田さんへ連絡  `t003`
   山田さん（DM）
   → 次の一手: 返事が来ていなければ再送する
   📝 11/14のメモ: 山田さんに電話済み、返事待ち
```

メモは本人が書いたものなので、言い換えたり要約したりしない。

**タスクIDを併記する。** 番号は日ごとに変わるがIDは変わらない。
「t091完了」という返し方もできるようにするため。

推測した期限には必ず `(推定)` を付ける。

**1件もなければ**、親に「:sparkles: 対応が必要なものはありません」とだけ書き、子スレッドは付けない。

## 4.5 持っている案件の一覧を更新する

管理者のページ（ダッシュボード）が知りたいのは、その日に拾ったタスクではなく、
**「この人がいま、どの案件（プロジェクト・取り組み）を持っているか」**。
そのために手元に**持ち案件の台帳**（`$H/data/projects.json`）を置き、毎朝、動きがあった案件だけを更新する。
管理者に届くのはこの一覧（案件名・関わり方・状態・段階・次の節目・いまの状態の一言・詳細・最後に動いた日）だけ。タスクの題名や件数は届かない。

```
bash "${CLAUDE_PLUGIN_ROOT}/bin/mietask" projects list
bash "${CLAUDE_PLUGIN_ROOT}/bin/mietask" share hints
```

`projects list` が今の一覧。`share hints` は案件名の手がかり（本人が関わる MTD の案件名と、同じチームの人が使っている案件名）。
動きの無い日が続いた案件は実行ファイルが扱う（**3週間で「しばらく動きなし」、6週間で一覧から外れる**）。こちらで消したり日付を直したりしない。

### 一覧が空のとき（最初の1回）：持っている案件を洗い出す

直近1か月を見て、本人が**いま持っている**案件を全部挙げる。その日のタスクに出てこないものも入れる。

- Slack：本人が直近1か月に発言したチャンネル（`from:<@本人のID> after:<1か月前>` で探す）。`pjt_〇〇`（プロジェクト）・`cdn_〇〇`（コーディネーター）は「〇〇」がそのまま案件
- カレンダー：直近2週間と先2週間の会議。定例・打合せの題名に出てくる案件・取り組み
- MTD：`share hints` の MTD の案件名
- タスク台帳：未完了のタスク（`tasks.json` の open・next・doing・blocked・later）
- 議事録・メール：本人が担当になっている取り組み

1回きりの用事（出欠の返事・単発の問い合わせ）は案件にしない。続いている仕事のまとまりだけを挙げる。

**根拠の強さで分ける。** 最初の一覧に本人が直さなければならない案件が混ざると、ページを見た管理者が誤解する。
次のどれかに当たる案件は根拠が弱いので、`touched` に入れず「確かめたい案件」として投稿で本人に聞く（4 の子スレッド 6）。

- カレンダーの題名だけが手がかりで、Slack・メール・議事録・タスク台帳・MTD のどれにも出てこない
- 直近2週間、本人の発言・メール・タスクの動きが無い（もう終わっている・手を離れていることが多い）
- 名前からは何の案件か決めきれず、別の案件と取り違えているかもしれない

根拠が強いもの（本人が最近発言している `pjt_`・`cdn_` のチャンネル、MTD の担当、未完了のタスクがある案件）はそのまま入れる。
**1つの会議の題名に2つの案件名が入っている**とき（例：「A校・B校 合同打合せ」）は、別々の案件として扱う。1つにまとめない。

確かめたい案件は、本人が「〇〇も持っている」と言えば翌朝から足す（会話の表を参照）。何も言われなければ足さない。

### 毎朝：動きがあった案件を更新する

今日の巡回（2・3）と前日の返信（1）を見て、**今日動きがあった案件**だけを `touched` に入れる。

- 一覧にある案件に動きがあれば、**一覧と同じ名前**で入れる（一言と状態を今日のものにする）
- 一覧に無い案件が出てきたら、新しく入れる（足される）
- 動きの無かった案件は入れない（最後に動いた日がそのまま残り、日がたつと実行ファイルが扱う）
- 本人が「〇〇は終わった」「〇〇は持っていない」と言った案件は `remove` に入れる。
  外した案件は90日覚えておかれ、巡回で関係するものを拾って `touched` に入れても足されない（「外した案件なので足しませんでした」と出る）。
  これは正しい動きなので、名前を変えて入れ直したりしない。本人が「〇〇はまた持った」と言ったときだけ、`restore` に入れて `touched` にも入れる
- 同じ案件が2つの名前で並んでいたら `rename` で1つにする

`"$T/projects.json"` に書く。**Writeツールで書く。**

```json
{"touched": [
  {"name": "渋谷区WS", "role": "PM", "stage": "仕上げ", "next": "当日の進行を先方と最終確認", "next_date": "2026-12-01", "note": "当日の進行案を先方に確認中", "detail": "12/5の授業に向けて、当日の進行案とワークシートを先方の先生に確認してもらっている。返事が来たら講師と最終の打合せを入れる", "state": "相手待ち"},
  {"name": "社内DX", "role": "リード", "stage": "進行中", "next": "見直し案を定例で決める", "note": "経費精算の流れの見直し", "state": "動いている"}
 ],
 "remove": ["昔の案件"],
 "restore": [],
 "rename": [{"from": "渋谷区ワークショップ", "to": "渋谷区WS"}]}
```

```
bash "${CLAUDE_PLUGIN_ROOT}/bin/mietask" projects update --file "$T/projects.json"
```

**名前の決め方**（上から順に使う。前の日と同じ案件には必ず同じ名前を使う）

1. 一覧にすでにある名前
2. MTD の案件名（手がかりの名前を一字も変えずに使う）
3. Slack のチャンネル名：`pjt_〇〇`・`cdn_〇〇` → 「〇〇」
4. 同じチームの人の手がかりにある名前
5. どれにも当たらなければ、社内で通じる短い呼び方（例：「社内DX」「ミエタスク開発」「採用広報」）

- `name` は**短く（20字くらいまで、30字が上限）**。括弧で中身を並べない（「つくりあい（11/21イベント・MAB）」ではなく「つくりあい」。中身は一言へ）
- `role` は関わり方（PM・CC・SP・リード・担当・手伝い・連携など、12字まで）。MTD の案件なら MTD の役割
- `note` は**いまの状態の一言**（40字まで）。管理者が「この人はこの案件でいまこれをやっている」と分かる粒度で書く（例：「当日の進行案を先方に確認中」「2学期ワークシートの仕上げ」）
- `detail` は**詳細**（3〜5文・200〜300字。300字が上限）。ページでは一言の下にトグルで開く。
  次の4つを、管理者が読んで状況をつかめるように書く：何のための案件か（相手・目的）／いま何をしていて、何が決まったか／
  詰まっていること・相手待ちのこと／次に何をするか（いつまでに）。日付は分かるものを入れる
  前の日と変わらなければ省いてよい（前の詳細が残る）。最初の1回は全部の案件に書く。入れないものは一言と同じ
- `stage` は**段階**。`準備`（構想・下調べ・関係者との調整を始めたところ）／`進行中`（作る・進める作業の本体）／
  `仕上げ`（本番・納品・リリースの直前、最終確認）／`運用中`（出来上がって回している・続いている保守や支援）のどれか。
  ページでは4つのバーで出るので、管理者が一目でどこまで来たか分かるように付ける。段階が変わった日だけ書けばよい（前のものが残る）
- `next` は**次の節目**（30字まで）。次に何が起きるか・何を終えれば一歩進むか（例：「項目を固める打合せ」「テスト用リンクを渡す」）。
  `next_date` はその日付（`yyyy-mm-dd`）。**会議の予定や本文に明記された日付だけ**を入れ、推測の日付は入れない（無ければ書かない。ページでは「日付未定」と出る）。
  節目が過ぎたら、その日のうちに次の節目に書き換える（書き換えると日付も入れ替わる）
- `state` は `動いている` / `相手待ち` / `期限が過ぎたものあり` のどれか。
  `期限が過ぎたものあり` は、その案件のタスクに**期限が今日より前**（今日は含まない）のものが残っているときだけ。全部が相手の返事待ちなら `相手待ち`、ほかは `動いている`
- 入れないもの：タスクの題名をそのまま写したもの、人の名前（社内・社外とも）、社外の会社・団体名（案件名に入っている学校名・自治体名は除く）、金額、メールや DM の件名・文面、リンク・メンション・メールアドレス、内々の話（人事・評価・採用の個別の人・健康・家族・お金・個人の相談）
- `$H/config.json` の `share.exclude`（本人が「管理者に出さないで」と言った案件名）に当たるものは入れない。一覧にあれば `remove` に入れる

形が違うと台帳は変わらずに止まるので、出力のとおりに直す。

## 5. 書式はSlackのmrkdwn

GitHub記法ではない。間違えると記号がそのまま見える。

- 太字は `*太字*`（`**太字**` ではない）
- リンクは `<https://… |表示名>`（`[表示名](https://…)` ではない）
- 箇条書きの点は `•` を自分で書く（`- ` は点にならない）
- 1メッセージは3900文字まで。超えると投稿の前に止まる。区分を分けるか件数を絞る

## 6. 投稿する

payloadを **`"$T/task-check-payload.json"`** に書く。**Writeツールを使う。**

```json
{"parent": "…", "replies": ["…", "…"]}
```

まず中身を確認する:
```
bash "${CLAUDE_PLUGIN_ROOT}/bin/mietask" post --payload "$T/task-check-payload.json" --projects --dry-run
```

警告が出たら payload を直してから、投稿する:
```
bash "${CLAUDE_PLUGIN_ROOT}/bin/mietask" post --payload "$T/task-check-payload.json" --projects
```

**一覧が出るのは自分のチャンネルだけ。** 実行ファイルは投稿のあとで次の2つを管理台帳に送る
（管理者に何が届いているかは、本人がミエタスクのページの「自分」で見られるので、投稿には出さない）。題名・メモ・出どころは送らない（DM・非公開チャンネル・メールの内容が入るため）。

| 送るもの | 見る人 |
|---|---|
| 持っている案件の一覧（案件名・関わり方・状態・段階・次の節目・一言・詳細・最後に動いた日） | 管理者のページ（本人・チームの管理者。役員・部門長は下のチームの分も） |
| 件数（超過・今日・今週） | システム管理者だけ（動作の点検用） |

**自分のチャンネルへの投稿は承認不要。** 想定内の動作。

出力に `警告: 点検用の件数を送れませんでした` や `警告: 持っている案件を窓口に送れませんでした` が出たら、
**自分用の投稿は済んでいるので、投稿はやり直さない。** 一覧は警告に出たとおり `share --projects` だけをやり直す。
7 の記録はそのまま進め、失敗したことを最後の報告に書く。

## 7. スレッドを控える

投稿の出力に `ts: 1794411398.212869` の行が出る。その値を渡す。
**これを忘れると、翌朝の完了反映が動かない。**

```
bash "${CLAUDE_PLUGIN_ROOT}/bin/mietask" sync record --ts <出力されたts>
```

## 8. 失敗したとき

実行ファイルはエラーに対処法を添えて止まる。握りつぶさない。

- 同じコマンドを闇雲に再実行しない。**エラーメッセージを読んで原因を直す**
- 子スレッドの途中で落ちた場合、**親とそこまでの子は投稿済みで残っている。**
  投げ直すと二重になるので、残りだけを `thread_ts` 指定で投げるか、本人に報告する。
  その場合も親の ts は 7 で必ず控える
- トークン切れ・スコープ不足・Botが退出などは自分で直せない。
  **何が起きたかを報告して止まる。** 原因が分からなければ `bash "${CLAUDE_PLUGIN_ROOT}/bin/mietask" doctor` を実行して、❌ の行を報告に含める
- 「管理台帳で停止されています」と出たら、投稿はされていない。そのまま報告して止まる（再実行しない）
- 台帳が壊れたら `~/.mietask/data/tasks.json.bak_*`（直近30件が残っている）から戻す。自力で直そうとしない

## 会話で扱いを変えたいと言われたとき

番号はその日の投稿の通し番号。まず対応を確かめてから動かす:

```
bash "${CLAUDE_PLUGIN_ROOT}/bin/mietask" sync thread
```

`mapping` の番号から task.id を引く（`t091` のようにIDで言われたらそのまま使う）。

| 言われたこと | やること |
|---|---|
| 「3は対応不要」「これは要らない」 | `bash "${CLAUDE_PLUGIN_ROOT}/bin/mietask" sync status <id> --status dropped --note "本人: 対応不要"`。以後出ない |
| 「3は来週にする」「今週はやらない」 | `bash "${CLAUDE_PLUGIN_ROOT}/bin/mietask" sync status <id> --status later`。巡回で拾われたときだけ出る |
| 「2は〇〇さん待ち」 | `bash "${CLAUDE_PLUGIN_ROOT}/bin/mietask" sync status <id> --status blocked --note "〇〇さん待ち"`。相手待ちの欄に移る |
| 「〇〇からのメールは出さなくていい」「このチャンネルは見なくていい」 | `$H/config.json` の `gmail.exclude_senders`（送信元のアドレス）か `slack.exclude_channels`（チャンネルID）に足す。**Editツールで、既存の項目は消さない。** 足す前に、何を足すかを本人に一言で確かめる。あわせて今出ている該当タスクは上の「対応不要」と同じく dropped にする |
| 「〇〇は管理者に出さないで」 | `$H/config.json` の `share.exclude`（文字列の配列。無ければ作る）に案件名を足す。**Editツールで、既存の項目は消さない。** あわせて `bash "${CLAUDE_PLUGIN_ROOT}/bin/mietask" projects remove "〇〇"`。すでに届いた分は翌朝の一覧で置き換わる |
| 「〇〇は終わった」「〇〇は持っていない」 | `bash "${CLAUDE_PLUGIN_ROOT}/bin/mietask" projects remove "〇〇"`。翌朝の一覧から消え、90日は巡回で拾っても戻らない |
| 「〇〇はまた持った」「〇〇も持っている」 | `"$T/projects.json"` に `{"restore": ["〇〇"], "touched": [{"name": "〇〇", "state": "動いている", "note": "…"}]}` を書いて `projects update`（外していない案件なら `restore` は要らない） |
| 「〇〇と△△は同じ案件」 | `"$T/projects.json"` に `{"rename": [{"from": "〇〇", "to": "△△"}]}` を書いて `projects update` |
| 「3終わった」 | **ここでは done にしない。** その日の投稿に「3完了」と返信してもらう（完了は返信からだけ記録する作り） |

- どれかわからないときは、タイトルを読み上げて確かめてから動かす
- `done` / `dropped` のものを戻したいと言われても `--reopen` は本人の明示があるときだけ

## やらないこと

- **自分のチャンネル以外に投稿しない。** 他人が見る場所に顧客名や依頼内容を出さない
- 題名やメモを、自分のチャンネルの外へ別の手段で送らない。外に出るのは実行ファイルが送る持ち案件の一覧（4.5）と点検用の件数だけ
- **返信案を実際に送らない。** メール送信・Slack投稿（自分のチャンネルを除く）・
  カレンダーの作成/変更/削除・Notionの更新は**提案までで止める**
- **`tasks.json` を手で編集しない。** 必ず `mietask sync` を通す
- タスクを削除しない。`status` を変えるだけ
- `done` / `dropped` を `open` に戻さない（実行ファイルが防いでいる。回避しようとしない）
- 本人が「対応不要」と言ったものを再提示しない

## 終わったら

次を1〜2行で報告する。

- 投稿したスレッドのpermalink と 各区分の件数
- 持っている案件の数と、今日足した・外した案件
- 完了反映の結果（done にした件数、解決できなかった返信があればその内容）
- 新規登録した task.id
