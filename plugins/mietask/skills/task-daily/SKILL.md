name: task-daily
description: Slack・Gmail・Googleカレンダーを巡回し、自分が対応すべきタスクを親＋子スレッドの形で自分のSlackチャンネルに投稿する。あわせて前日のスレッドに入った「N完了」をタスク台帳に反映する。毎朝の定期実行から呼ばれるほか、「今日のタスク投稿して」「巡回して投稿」と言われたときにも使う。「3は対応不要」「これは要らない」「3は来週にする」「2は〇〇さん待ち」のように、一覧の番号を指してタスクの扱いを変えたいと言われたときも使う。
---

自分のタスクを巡回し、結果をSlackの自分専用チャンネルに投稿する。
あわせて、前日のスレッドへの返信（完了・ステイ・メモ・追加）を台帳に反映する。

## 置き場所

| | パス |
|---|---|
| 実行ファイル | `${CLAUDE_PLUGIN_ROOT}/bin/mietask`（Mac・Windows 共通。追加のインストール不要） |
| データ | `~/.mietask/`（`MIETASK_HOME` で変更可） |
| 設定 | `~/.mietask/config.json` |

**最初に `$H/config.json` を読む**（`$H` の求め方は下の「Mac でも Windows でも」を参照）。 本人の名前・メール・SlackユーザーID・
投稿先チャンネル、および巡回の除外ルールがそこにある。

設定が無ければセットアップが済んでいない。`/mietask:setup` を案内して止まる。

**`tasks.json` は唯一の正。手で編集しない。** 登録と完了反映は必ず
`mietask sync` を通す（バックアップと原子的な置き換えが入っている）。

以下 `$B` = `${CLAUDE_PLUGIN_ROOT}/bin/mietask` とする。

**Mac でも Windows でも同じ手順で動かす。**

- 処理は必ず `bash "$B" <コマンド> [引数]` で呼ぶ。パスは必ず `"…"` で囲む
- 一時ファイルは `/tmp` ではなく `$T` に書く。最初に次を実行し、出てきた絶対パスを `$H`・`$T` とする。
  Writeツール・Readツールに渡すパスには `~` を使わず、この絶対パスを使う

```
bash "$B" paths home
bash "$B" paths tmp
```

---

## 1. 前日の返信を反映する

```
bash "$B" sync thread
```

`ts` が出なければ初回。この節を飛ばして2へ。

`ts` が出たら、そのスレッドを `slack_read_thread`（channel_id はその `channel`、
message_ts はその `ts`）で読み、返信を次の形で `"$T/task-replies.json"` に書く。
**Writeツールで書く。heredoc や `cat >` は使わない。**

```json
[{"user": "U01ABCDEFG", "text": "1完了"}, {"user": "...", "bot_id": "...", "text": "..."}]
```

`user` と `bot_id` は読み取れたものをそのまま入れる。**省略しない。**
Botが投げた子スレッドを本人の発言と取り違えると、無関係なタスクが done になる。

**本人の返信が0件でも、読み取った返信をそのまま書く（Botの子スレッドしか無ければ、それだけを書く）。**
ファイルを書かずに先へ進まない。

```
bash "$B" sync complete --replies "$T/task-replies.json"
```

**入力ファイルは、使い終わると実行ファイルが消す**（返信・巡回結果・投稿内容のどれも）。
前の実行のファイルが残っていると、書き直せなかったときに古い中身で台帳を書き換えてしまうため。
`見つかりません` / `no such file` と出たら、書き込みに失敗している。**もう一度書いてから**実行する。
古いファイルを探して使い回さない。

返信は次の4種類を受ける。実行ファイルが判別するので、こちらで解釈し直さない。

| 返信 | 反映 |
|---|---|
| `1完了` | done にする。翌日から出ない |
| `2ステイ` | 明日もそのまま出す。相手待ち・保留中のものでも翌朝は必ず出る |
| `3 メモ本文` | そのタスクにメモを残す。翌朝の一覧に「前回のメモ」として出る |
| `追加 見積書を作る 11/20まで` | 新しいタスクとして足す。日付があれば期限になる |

`2ステイ 来週の会議で決める` のようにステイとメモを同時に書いてもよい。

**追加は、巡回で拾えない仕事を本人が手で入れるための道。** 巡回はSlack・Gmail・カレンダー・議事録に
出てきたものしか拾えないので、口頭で頼まれたことや自分で決めた仕事はここから入る。
足したタスクは翌朝の upsert で「巡回では拾われなかったが、未完了なので一覧に載せるもの」として出る。

出力の「⚠ 解決できず」「⚠ 該当なし」は**黙って流さない。** 最後の報告に含める。

すでに `done` のものは「変更なし」と出る。同じスレッドを二度読んでも、
ステイの回数やメモが二重に増えることはない。

## 2. 巡回する

`task-check` スキルを使って Slack・Gmail・Googleカレンダーを巡回する。
スキルの指示に従いつつ、`config.json` の除外ルールを必ず通す。

**判定軸は「自分が何かをしないと前に進まないか」だけ。** 迷ったら拾う。

- **未読・受信トレイ在中は「要対応」の目印に使わない。** 受信トレイを整理していない人が
  多く、未読が数千件あることも珍しくない。`config.gmail` の除外を通してノイズを落とす
- 巡回できなかったサービス（未接続・エラー）は**黙って省略しない。**
  「Notion: 未接続のためスキップ」のように明記する
- 議事録が自動でメールに届く環境なら、そこから**自分の名前が付いたアクションだけ**を拾う
  （`config.meeting_notes`）
- 対面の打合せは議事録が取れない。該当しそうな予定が直前にあれば、その旨を書く

## 3. 台帳に登録する

巡回で拾ったものを `"$T/task-findings.json"` に書く。**Writeツールで書く。**
**表示したい順**（期限超過 → 今日中 → 今週中 → 予定の確認 → 相手待ち）に並べる。
この配列の順が、そのまま表示番号 1, 2, 3… になる。

```json
[{
  "title": "見積書の内容を確認して返信",
  "section": "overdue",
  "priority": "P1",
  "due": "2026-10-31",
  "due_confidence": "explicit",
  "next_action": "金額の根拠を確認し、問題なければ承認を返す",
  "notes": "",
  "source": {"app":"slack","ref":"slack:C01ABCDEFG:1793867033.987339","url":"https://...","from":"〇〇さん(DM)"}
}]
```

- `section` は `overdue` / `today` / `week` / `watch` / `waiting` のどれか
- `source.ref` は**突合の唯一の鍵。** Slackは `slack:<channel>:<thread_ts>`、
  Gmailは `gmail:<threadId>`、カレンダーは `calendar:<eventId>`、議事録は `meeting:<id>`。
  同じ案件には必ず同じrefを使う。**ここがブレると毎朝重複登録される**
- `due_confidence` は本文に明記があれば `explicit`、文脈からの推測なら `inferred`
- **推測で金額・期限・担当者を埋めない。** 読み取れないなら notes に「要確認」と書く

```
bash "$B" sync upsert --findings "$T/task-findings.json"
```

出力の「表示番号 → task.id」を**そのまま使う。** 番号を自分で振り直さない。
「除外」として出たものは投稿に載せない（完了済み・却下済み）。

**「巡回では拾われなかったが、未完了なので一覧に載せるもの」も必ず投稿に載せる。**
巡回はSlack・Gmail・カレンダーを見るだけなので、台帳にあって今日は誰も触れていない
タスクは、これが無いと永久に沈む。**期限超過を落とすのが最悪。**
出力に区分・ID・期限・次の一手が入っているので、該当区分に混ぜて期限が古い順に並べる。

## 4. 投稿用のpayloadを組み立てる

親メッセージ1本＋子スレッド最大5本。番号は3の出力どおり。

**親**
```
:date: *M/D(曜) HH:MM*  :warning:超過N / :red_circle:今日N / :large_yellow_circle:今週N

1. 最重要タスクの見出し ← 一言理由
2. …
3. …

詳細はスレッドに。返信で「1完了」「2ステイ」「3 メモ」「追加 〇〇」が書けます。
```
上位3件まで。該当0件の区分は件数表記からも落とす。

**子スレッド**（順番を守る。該当0件の区分はスレッドごと省く）

| | 中身 |
|---|---|
| 1 | :warning: 期限超過（全件・次の一手つき・何日超過かを書く） |
| 2 | :red_circle: 今日中 |
| 3 | :large_yellow_circle: 今週中（上位5件＋「…他N件」。黙って切らない） |
| 4 | :calendar: 予定の確認事項／:hourglass_flowing_sand: 相手待ち |
| 5 | :speech_balloon: 返信案（コピペ用のコードブロック） |

各タスクは `番号. タイトル  \`tNNN\`` → 出所（可能ならpermalink）→ `→ 次の一手: …` の順。

upsert の出力に「前回のメモ・ステイ」があれば、そのタスクの次の一手の下に**そのまま**添える。

```
3. 山田さんへ連絡  `t003`
   山田さん（DM）
   → 次の一手: 返事が来ていなければ再送する
   📝 11/14のメモ: 山田さんに電話済み、返事待ち
```

メモは本人が書いたものなので、言い換えたり要約したりしない。

**タスクIDを併記する。** 番号は日ごとに変わるがIDは変わらない。
「t091完了」という返し方もできるようにするため。

推測した期限には必ず `(推定)` を付ける。

**1件もなければ**、親に「:sparkles: 対応が必要なものはありません」とだけ書き、子スレッドは付けない。

## 5. 書式はSlackのmrkdwn

GitHub記法ではない。間違えると記号がそのまま見える。

- 太字は `*太字*`（`**太字**` ではない）
- リンクは `<https://… |表示名>`（`[表示名](https://…)` ではない）
- 箇条書きの点は `•` を自分で書く（`- ` は点にならない）
- 1メッセージは3900文字まで。超えると投稿の前に止まる。区分を分けるか件数を絞る

## 6. 投稿する

payloadを **`"$T/task-check-payload.json"`** に書く。**Writeツールを使う。**

```json
{"parent": "…", "replies": ["…", "…"]}
```

まず中身を確認する:
```
bash "$B" post --payload "$T/task-check-payload.json" --dry-run
```

警告が出たら payload を直してから、投稿する:
```
bash "$B" post --payload "$T/task-check-payload.json"
```

**一覧が出るのは自分のチャンネルだけ。** 投稿のあと、実行ファイルが**件数（超過・今日・今週）だけ**を
管理台帳に送る。システム管理者が動作を点検するのに使う（チームの管理者には見せない）。題名・メモ・出どころは送らない
（DM・非公開チャンネル・メールの内容が入るため）。`--dry-run` のときは、送る件数だけが表示される。

**自分のチャンネルへの投稿は承認不要。** 想定内の動作。

出力に `警告: 点検用の件数を送れませんでした` が出たら、**自分用の投稿は済んでいるのでやり直さない。**
7 の記録はそのまま進め、失敗したことを最後の報告に書く。

## 7. スレッドを控える

投稿の出力に `ts: 1794411398.212869` の行が出る。その値を渡す。
**これを忘れると、翌朝の完了反映が動かない。**

```
bash "$B" sync record --ts <出力されたts>
```

## 8. 失敗したとき

実行ファイルはエラーに対処法を添えて止まる。握りつぶさない。

- 同じコマンドを闇雲に再実行しない。**エラーメッセージを読んで原因を直す**
- 子スレッドの途中で落ちた場合、**親とそこまでの子は投稿済みで残っている。**
  投げ直すと二重になるので、残りだけを `thread_ts` 指定で投げるか、本人に報告する。
  その場合も親の ts は 7 で必ず控える
- トークン切れ・スコープ不足・Botが退出などは自分で直せない。
  **何が起きたかを報告して止まる。** 原因が分からなければ `bash "$B" doctor` を実行して、❌ の行を報告に含める
- 「管理台帳で停止されています」と出たら、投稿はされていない。そのまま報告して止まる（再実行しない）
- 台帳が壊れたら `~/.mietask/data/tasks.json.bak_*`（直近30件が残っている）から戻す。自力で直そうとしない

## 会話で扱いを変えたいと言われたとき

番号はその日の投稿の通し番号。まず対応を確かめてから動かす:

```
bash "$B" sync thread
```

`mapping` の番号から task.id を引く（`t091` のようにIDで言われたらそのまま使う）。

| 言われたこと | やること |
|---|---|
| 「3は対応不要」「これは要らない」 | `bash "$B" sync status <id> --status dropped --note "本人: 対応不要"`。以後出ない |
| 「3は来週にする」「今週はやらない」 | `bash "$B" sync status <id> --status later`。巡回で拾われたときだけ出る |
| 「2は〇〇さん待ち」 | `bash "$B" sync status <id> --status blocked --note "〇〇さん待ち"`。相手待ちの欄に移る |
| 「〇〇からのメールは出さなくていい」「このチャンネルは見なくていい」 | `$H/config.json` の `gmail.exclude_senders`（送信元のアドレス）か `slack.exclude_channels`（チャンネルID）に足す。**Editツールで、既存の項目は消さない。** 足す前に、何を足すかを本人に一言で確かめる。あわせて今出ている該当タスクは上の「対応不要」と同じく dropped にする |
| 「3終わった」 | **ここでは done にしない。** その日の投稿に「3完了」と返信してもらう（完了は返信からだけ記録する作り） |

- どれかわからないときは、タイトルを読み上げて確かめてから動かす
- `done` / `dropped` のものを戻したいと言われても `--reopen` は本人の明示があるときだけ

## やらないこと

- **自分のチャンネル以外に投稿しない。** 他人が見る場所に顧客名や依頼内容を出さない
- 題名やメモを、自分のチャンネルの外へ別の手段で送らない。外に出るのは実行ファイルが送る点検用の件数だけ
- **返信案を実際に送らない。** メール送信・Slack投稿（自分のチャンネルを除く）・
  カレンダーの作成/変更/削除・Notionの更新は**提案までで止める**
- **`tasks.json` を手で編集しない。** 必ず `mietask sync` を通す
- タスクを削除しない。`status` を変えるだけ
- `done` / `dropped` を `open` に戻さない（実行ファイルが防いでいる。回避しようとしない）
- 本人が「対応不要」と言ったものを再提示しない

## 終わったら

次を1〜2行で報告する。

- 投稿したスレッドのpermalink と 各区分の件数
- 完了反映の結果（done にした件数、解決できなかった返信があればその内容）
- 新規登録した task.id
